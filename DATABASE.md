# Database Design (Logical Layer)

ProjectMind does not use a traditional database daemon (like PostgreSQL or MongoDB) to ensure it remains a lightweight, portable, offline-first tool. Instead, the "Database" is a logical layer built on top of flat files managed within the `.projectmind` directory.

## 1. Storage Engine Architecture

The persistence layer acts as a rudimentary embedded NoSQL document/graph store.

* **Storage Format:** Standard UTF-8 text files (`.json`, `.jsonl`, `.md`).
* **ACID Properties:**
  * **Atomicity:** File writes use an atomic rename strategy (write to `.tmp`, then `mv`).
  * **Consistency:** Managed via schema validation prior to write.
  * **Isolation:** Enforced via a physical `.lock` file in the directory.
  * **Durability:** Relies on the host OS filesystem sync.

## 2. Logical Components

### 2.1 The Key-Value Store (`state.json`)
Used for fast lookups of global metadata.
* **Keys:** `schema_version`, `last_commit_hash`, `last_update_timestamp`, `project_name`.

### 2.2 The Graph Store (`graph.json`)
Stores the structural relationships extracted from the code.
* Implemented as an adjacency list in JSON.
* Optimized for fast reads of a node's edges (e.g., "What files depend on this file?").
* Memory-mapped (or read entirely into RAM) during the `projectmind update` cycle due to the typical small size of AST graphs (usually < 50MB for large projects).

### 2.3 The Time-Series Log (`history.jsonl`)
Stores the sequential semantic summaries generated by the LLM.
* Implemented as JSON Lines (`.jsonl`).
* Append-only. Extremely fast writes.
* Easy to tail or parse sequentially without loading the whole file into memory.

### 2.4 The Materialized View (`context.md`)
The final output designed strictly for AI Agent consumption.
* Materialized during every update cycle.
* Read-heavy (read by the AI Agent multiple times per session).
* Write-light (written only once per `projectmind update`).

## 3. Concurrency Control

Multiple AI agents (or a human and an agent) might try to run `projectmind update` simultaneously.
* **Mechanism:** Lockfile (`.projectmind/update.lock`).
* **Process:**
  1. Process attempts to create `update.lock`.
  2. If it exists, check the PID inside. If the PID is dead, delete it and claim the lock.
  3. If the PID is alive, fail with `EBUSY` and exit gracefully.

## 4. Query Access Patterns

Since we use flat files, complex queries must be handled in application memory.
* **Pattern 1: Context Hydration (Agent Read)**
  * AI Agent reads `context.md` directly. No ProjectMind execution required. Speed: ~1ms.
* **Pattern 2: Graph Traversal (Internal Use)**
  * ProjectMind loads `graph.json` into a memory-based graph structure (e.g., using `networkx` in Python or similar in TS) to find dependencies. Speed: ~100ms.
* **Pattern 3: History Consolidation**
  * ProjectMind streams `history.jsonl` line-by-line to feed into the LLM for summarization. Memory overhead is $O(1)$.
