# Workspace Lifecycle & Health

This document defines the overarching lifecycle of the Global Workspace itself (the `~/.projectmind` or `%LOCALAPPDATA%` directory), and the robust health monitoring system that protects it.

## 1. Global Workspace Lifecycle

While individual repositories have their own lifecycle (`REPO_LIFECYCLE.md`), the Global Workspace is a singleton instance per user machine.

### 1.1 Create
Triggered implicitly on the first run of any ProjectMind v2.0 command.
* `WorkspacePathResolver` determines the OS-specific directory.
* `WorkspaceManager` creates the root folders (`registry/`, `config/`, `models/`, `workspaces/`, etc.).
* Initializes an empty SQLite registry database with all required schemas.

### 1.2 Load
Occurs on daemon startup or CLI execution.
* Connects to the central SQLite Registry.
* Loads global configuration (`config/config.json`).
* Mounts available local SLM/LLM models and plugins.

### 1.3 Upgrade
Managed by the `MigrationEngine`. When a new ProjectMind binary is installed:
* Checks the registry schema version.
* Applies rolling SQL migrations if necessary.
* Upgrades default configurations without overwriting user overrides.

### 1.4 Backup & Recover (Global)
* **Backup:** Creating a snapshot of the entire Global Workspace (excluding large `cache/` and `models/` folders) for system migration.
* **Recover:** Restoring a Global Workspace to a new machine, requiring subsequent `relink` commands for all repositories.

### 1.5 Destroy
A complete uninstallation mechanism. Deletes the entire OS-specific ProjectMind directory, severing the link to all local `.projectmind.json` pointers.

## 2. Workspace Health Monitor

The `WorkspaceHealthMonitor` is a critical subsystem introduced in v2.0 to ensure the integrity of decoupled data. It forms the foundation of the `projectmind doctor` command.

### 2.1 Validation Scenarios

The Monitor continually (or manually via CLI) checks the following:

1. **Registry Consistency:** Are there duplicate UUIDs? Do the workspace IDs in the SQLite DB match the folders that actually exist on disk?
2. **Missing Repositories:** Does the physical repository path logged in the Registry still exist on the user's hard drive? (If not, flag as `orphaned`).
3. **Broken Pointer Files:** Does the local `.projectmind.json` contain valid JSON? Does the UUID match the Registry?
4. **Database Integrity:** Runs internal checksums (e.g., `PRAGMA integrity_check` for SQLite) on the `registry.db` and repository-specific KuzuDB/SQLite files.
5. **Storage Corruption:** Checks for read/write permissions in the Global Workspace directory.
6. **Version Mismatches:** Detects if a repository workspace was generated by a newer, incompatible version of ProjectMind.
7. **Migration Status:** Identifies workspaces that failed a previous migration and require manual recovery.
8. **Plugin Compatibility:** Ensures globally installed plugins in `plugins/` are compatible with the current Kernel version.
9. **Model Availability:** Verifies that required SLM/LLM models referenced in the config exist in the `models/` directory and are not corrupted.
10. **Cache Health:** Detects bloated or malformed cache files in `cache/` and safely purges them.

### 2.2 Repair Mechanisms

When `projectmind doctor --repair` is executed:
* Rebuilds corrupted SQLite indexes.
* Clears orphaned cache files.
* Prompts the user to `relink` missing physical repositories.
* Redownloads missing or corrupt SLM models.

# Repository Lifecycle

This document defines the lifecycle states and transitions for a target repository managed by ProjectMind v2.0. Because data is stored in the Global Workspace, the repository's lifecycle is heavily focused on pointer management and registry synchronization.

## 1. Lifecycle States

1. **Unregistered:** The repository has no `.projectmind.json` file.
2. **Registered:** A UUID exists in the pointer file and the Global Registry.
3. **Initialized:** The Global Workspace directory structure (`workspaces/<uuid>/`) is provisioned.
4. **Active (Analyzed/Updated):** Data is actively being extracted and stored.
5. **Archived:** Data is compressed for cold storage, workspace freed.
6. **Orphaned:** Pointer file exists, but workspace data is missing (or vice versa).

## 2. Core Operations

### 2.1 Register & Initialize
When a user runs `projectmind init` in a new repository:
1. `RepositoryIdentityManager` generates a UUID (e.g., `123e4567-e89b-12d3-a456-426614174000`).
2. Creates `.projectmind.json` in the local repository.
3. `WorkspaceManager` creates the subsystem folders in the Global Workspace (`workspaces/<uuid>/state`, `intelligence`, etc.).
4. `RegistryService` inserts the path and UUID into the SQLite `registry.db`.

### 2.2 Analyze & Update
When a user runs `projectmind update`:
1. `WorkspaceLocator` reads the local `.projectmind.json`.
2. Locates the workspace via the `RegistryService`.
3. Validates health (e.g., checking for moved folders).
4. Executes the extraction and semantic pipelines, writing to the Workspace API.

### 2.3 Move & Relink
If a user moves the repository folder on their hard drive:
1. The next ProjectMind command will fail the `WorkspaceLocator` path check (the path in `registry.db` won't match the current physical path).
2. The user runs `projectmind relink`.
3. ProjectMind reads the UUID from the local `.projectmind.json`.
4. `RegistryService` updates the physical path for that UUID in `registry.db`.
5. Operation resumes seamlessly.

### 2.4 Rename
Similar to a Move operation. If the repository folder is renamed, a `relink` command synchronizes the new name and path with the Global Registry.

### 2.5 Backup & Restore
* **Backup:** `projectmind backup` zips the `workspaces/<uuid>/` folder and places it in the Global Workspace's `backups/` directory, logging the timestamp in the Registry.
* **Restore:** Overwrites the current workspace directory with a selected backup archive. The repository's `.projectmind.json` remains untouched.

### 2.6 Delete
Running `projectmind remove`:
1. Deletes `.projectmind.json` from the local repository.
2. `WorkspaceManager` deletes `workspaces/<uuid>/` from the Global Workspace.
3. `RegistryService` removes the entry from `registry.db`.

### 2.7 Archive & Recovery
* **Archive:** Compresses the workspace into cold storage and removes the active `workspaces/<uuid>/` folder, marking the status as `archived` in the Registry. Useful for saving disk space on inactive projects.
* **Recovery:** Unpacks an archived workspace back into the active `workspaces/` directory.
